# Reconocer SQL y los formatos de configuración

:::decision
Un agente de código no solo cambia programas: también cambia consultas SQL y archivos de configuración. Antes de aceptar uno de esos cambios, identifica en qué lenguaje o formato está escrito, qué valor controla qué comportamiento y qué regla de ese formato podría dejar el archivo inválido. En SQL, mira primero cómo se tratan los valores vacíos.
:::

:::quick-check
Si ya tienes práctica con esto, responde estas dos preguntas. Si aciertas ambas, puedes ir directo a la comprobación del final.

1. Una consulta usa `WHERE expected_close_date = NULL` para encontrar las oportunidades sin fecha de cierre. ¿Qué devuelve?
   - **Respuesta:** ninguna fila. Comparar con un valor nulo da «desconocido», no verdadero. Para buscar vacíos se escribe `IS NULL`.
2. Un archivo de ajustes en JSON tiene una línea que empieza con `//` para explicar un valor. ¿Qué problema hay?
   - **Respuesta:** JSON no admite comentarios, así que un programa que lo lea de forma estricta rechaza el archivo entero como inválido.
:::

## Cuatro archivos en un mismo cambio {#caso}

El agente que trabaja en el repositorio del pipeline entrega un cambio que toca cuatro archivos. Uno es una consulta SQL que cuenta oportunidades por región; otro, el archivo de :term[supuestos]{id=g-supuesto} en JSON; el tercero declara las dependencias de Python, es decir, los paquetes de código ajeno que el proyecto necesita para funcionar; y el cuarto es el flujo de integración continua (CI), el proceso automático que corre las pruebas cada vez que se envía un cambio al repositorio. Solo uno de los cuatro es Python, así que para revisar el cambio la analista necesita reconocer cada formato y saber dónde suele esconderse el error en cada uno.

## SQL: filtrar filas o filtrar grupos {#sql-filtrar}

SQL es el lenguaje con el que se consultan las tablas de una base de datos. Una consulta típica elige columnas (`SELECT`), la tabla (`FROM`), las filas que entran (`WHERE`) y cómo agruparlas (`GROUP BY`). Las funciones de agregado, como `count` (contar) o `sum` (sumar), resumen cada grupo en un solo valor.

El orden importa, porque `WHERE` filtra filas antes de agrupar y `HAVING` filtra grupos después. Por eso una condición sobre un agregado, como «regiones con más de diez oportunidades», va en `HAVING` y no en `WHERE` :cite[src-postgres-tutorial-agg].

## SQL: los valores vacíos {#nulos}

En SQL, un valor vacío se escribe `NULL` y significa «desconocido». Comparar cualquier cosa con `NULL` usando `=` no da verdadero ni falso, sino otro `NULL`, así que `WHERE fecha = NULL` no encuentra ninguna fila. Para preguntar por vacíos se usa `IS NULL` :cite[src-postgres-comparison].

Los agregados también tratan los vacíos de forma particular. `count(*)` cuenta filas, mientras que `count(columna)` cuenta solo las filas donde esa columna no está vacía. `sum` y `avg` (el promedio) ignoran los vacíos, y `sum` sobre cero filas devuelve `NULL`, no cero; para obtener cero se envuelve en `coalesce(sum(monto), 0)`, donde `coalesce` reemplaza el vacío por el valor que se le indica :cite[src-postgres-aggregate].

En los datos del curso, OPP-1021, del Centro, no tiene fecha de cierre. Una consulta con `count(*)` y `count(expected_close_date)` por región da dos cifras que difieren en uno en el Centro, y las dos son correctas: cuentan cosas distintas [inferencia].

Hay una trampa más, frecuente en cambios de agentes. `JOIN` une dos tablas a través de una columna que comparten, la clave; si esa clave se repite en una de ellas, cada fila se multiplica. En el :term[snapshot]{id=g-snapshot-datos}, OPP-1012 aparece dos veces, así que si se une sin quitar antes el duplicado, su monto se suma dos veces [inferencia].

## JSON: estricto y sin comentarios {#json}

JSON es el formato más común para que los programas intercambien datos. Admite objetos (pares de nombre y valor entre llaves), listas entre corchetes, números, textos entre comillas dobles y los literales `true`, `false` y `null`, siempre en minúscula. Dentro de un objeto, los nombres deberían ser únicos, porque si se repiten cada programa que lea el archivo puede quedarse con un valor distinto :cite[src-ietf-rfc8259]. La gramática de JSON no tiene comentarios [inferencia], y un lector estricto (un programa que interpreta el archivo sin tolerar desvíos) lo rechaza si encuentra un comentario o una coma después del último elemento.

El archivo de supuestos del caso es JSON. Una de sus líneas es `"duplicate_policy": "latest_last_activity"`, que le dice al cálculo que, ante una oportunidad repetida, conserve la fila con la actividad más reciente. Si un agente la cambia a `"highest_amount"`, el cálculo sigue corriendo sin errores y las cifras cambian [inferencia]. Por eso, en un archivo de configuración, cambiar un valor equivale a cambiar el comportamiento del programa.

## TOML: pares de clave y valor {#toml}

TOML es un formato de configuración pensado para ser mínimo. Se escribe en líneas `clave = valor`, admite comentarios con `#`, agrupa las claves en secciones con un encabezado entre corchetes, como `[project]`, y forma listas de secciones con doble corchete. Distingue mayúsculas de minúsculas, los valores de verdad van siempre en minúscula y tiene un tipo propio para fechas :cite[src-toml-v1].

En Python, el archivo `pyproject.toml` está escrito en TOML, y en él un proyecto declara sus dependencias y la versión mínima de Python, por ejemplo `requires-python = ">=3.11"`. La guía de empaquetado aconseja pensarlo dos veces antes de poner también un límite superior de versión :cite[src-pypa-pyproject].

## YAML: la sangría manda {#yaml}

YAML organiza los datos con sangría, y esa sangría tiene que hacerse con espacios, porque los tabuladores están prohibidos para sangrar. Los comentarios empiezan con `#`, y la versión 1.2 se diseñó para que todo JSON válido sea también YAML válido :cite[src-yaml-spec-122]. En el esquema básico de esa versión (el conjunto de reglas con que se interpretan los valores), solo `true` y `false` (con sus variantes en mayúscula) son valores de verdad; `yes`, `no`, `on` y `off` se leen como texto :cite[src-yaml-spec-122]. Algunas bibliotecas (los paquetes que leen YAML desde un programa) siguen reglas más antiguas, así que conviene no depender de esas palabras [inferencia].

Los flujos de integración continua de los servicios de repositorios suelen escribirse en YAML, y en :ref[el manual 3]{to=m03-l4#que-es} viste otro uso: una :term[skill]{id=g-skill} es un archivo `SKILL.md` que empieza con un bloque YAML (los :term[metadatos]{id=g-metadatos}, con `name` y `description`) seguido de Markdown :cite[src-agentskills-spec]. Buena parte de la configuración de los agentes está en estos formatos, y para dirigir un agente sirve más saber leerlos que saber escribir código [inferencia].

## TypeScript: reconocerlo basta {#typescript}

Es probable que veas código en TypeScript, el lenguaje de muchas aplicaciones web. Es JavaScript con tipos, es decir, con anotaciones como `: number` o declaraciones con `interface` y `type` que dicen qué clase de dato se espera. Esos tipos se revisan antes de ejecutar y después se borran, de modo que el programa se comporta igual que el JavaScript equivalente :cite[src-ts-handbook-from-scratch]. Por eso un error de tipo es un aviso que llega antes de ejecutar; los tipos no comprueban los datos reales mientras el programa corre [inferencia].

:::worked-example{title="Los cuatro archivos del cambio"}
**La consulta SQL.** El agente cambió `count(expected_close_date)` por `count(*)` en el conteo de oportunidades «con fecha». El Centro sube en uno, porque ahora cuenta también OPP-1021, que no tiene fecha. La consulta sigue funcionando, pero la cifra ya no mide lo que dice su nombre.

**El JSON de supuestos.** El agente agregó una línea `// política acordada con FP&A` arriba de `duplicate_policy`. El archivo deja de ser JSON válido, y el cálculo no puede leer sus supuestos.

**El `pyproject.toml`.** Apareció una dependencia nueva. No es un error de formato, pero en :ref[la lección 3]{to=m04-l3#dependencias} verás por qué merece tanta atención como el código.

**El flujo de CI en YAML.** Una línea quedó sangrada con un tabulador. El archivo deja de ser YAML válido y las pruebas no llegan a correr. Es un fallo de la configuración, no del código.
:::

::check-questions

:::summary
- En SQL, `WHERE` filtra filas antes de agrupar y `HAVING` filtra grupos después.
- `= NULL` nunca es verdadero: se usa `IS NULL`. `count(*)` y `count(columna)` cuentan cosas distintas, y `sum` de cero filas da `NULL`.
- Un `JOIN` con claves repetidas multiplica filas.
- JSON es estricto: comillas dobles, literales en minúscula y sin comentarios. Cambiar un valor de configuración cambia el comportamiento.
- TOML usa `clave = valor` y es el formato de `pyproject.toml`. YAML se sangra con espacios, nunca con tabuladores.
- TypeScript es JavaScript con tipos que se borran al ejecutar.
:::
